# 7 万星仓库教的安装路径是错的——整理 130 个 AI Skill 的踩坑记录

> 📌 本文已发表于掘金：https://juejin.cn/post/7671196739655352339


最近在做一个中文 AI Skills 库。整理过程中发现，这个领域的中文资源基本是空白——英文那边 `anthropics/skills` 16 万星、`awesome-claude-skills` 7 万星，但中文用户既看不懂说明，也不知道有哪些中文 skill 可用。

于是我收录了 130 个（其中 59 个中文原创），又自己写了 12 个填补空白场景。下面是这个过程中真实踩到的坑，有些可能对你有用。

---

## 坑一：7 万星仓库教的安装路径，是错的

这是最让我意外的一个。

`awesome-claude-skills`（7.1 万星）的 Getting Started 里写着：

```bash
mkdir -p ~/.config/claude-code/skills/
cp -r skill-name ~/.config/claude-code/skills/
```

我照着做，装完没生效。查了一圈才发现，我这台 macOS 上**实际生效的路径是 `~/.claude/skills/`**：

```bash
$ ls ~/.claude/skills/
baoyu-comic  baoyu-cover-image  baoyu-diagram  ...

$ ls ~/.config/claude-code/skills/
ls: 该目录不存在
```

后来用 Vercel Labs 的 `npx skills add` 安装，验证了一下它装到哪。

**补充更正（2026-08-07 复测，CLI 1.5.22）**：现在的行为比我最初写的更细一层——
文件实际落在 `~/.agents/skills/`（多家 agent 共用的通用目录），
然后在 `~/.claude/skills/` 建一个符号链接指过去：

```bash
$ ls -l ~/.claude/skills/
lrwxr-xr-x  github-readme-cn -> ../../.agents/skills/github-readme-cn
```

安装器建立符号链接后，两个路径下都能看到同一份 Skill。这里能确认的是文件布局；当时没有保留 Claude Code 的任务级自动触发记录，因此不把它写成客户端兼容性结论。
**但 `~/.config/claude-code/skills/` 依然不存在、依然不生效**——最初那个结论没变，
只是我把话说得更准了。

这件事本身也是个教训：**工具会变，写死的结论要定期复测。**

**教训**：高星不等于正确。这类文档在社区里互相抄，很少有人真的跑一遍。**遇到路径、命令这种可验证的东西，花 10 秒实测比信任星数靠谱。**

## 坑二：61 个链接里，有 1 个是 404

整理社区 skill 时，我从 awesome 列表里抓了 61 个 GitHub 链接。本来想直接收录，后来还是决定逐个调 GitHub API 验证一遍：

```python
for entry in entries:
    d = api(f"/repos/{owner}/{repo}")
    if "_err" in d:
        dead.append(entry)   # 404
```

结果：60 个正常，**1 个已经 404 了**（`threat-hunting-with-sigma-rules`）。

比例不高，但如果不验证，我的列表里就会有一条死链。而"链接会不会死"恰恰是这类导航项目最基本的信誉。

顺带一提，同一套方法用在工具导航上，先后发现了 4 个**域名迁移**：

- `cursor.sh` → `cursor.com`
- Windsurf 被 Cognition 收购，并入 Devin Desktop
- `blackforestlabs.ai` → `bfl.ai`（Flux）
- `runwayml.com` → `runway.com`

这些如果不做自动检测，列表里就一直挂着过期链接。

## 坑三：星数高 ≠ 官方出品

我给收录的 skill 打"官方"标签时，图省事写了这么一行：

```python
"official": e["stars"] > 150000
```

想法是：星数超过 15 万的肯定是 `anthropics/skills` 官方仓库。

结果 `obra/superpowers`（26 万星）也被标成了"官方"——它是个很优秀的社区框架，但**不是 Anthropic 官方**。5 个 skill 被误标。

改成按仓库地址判断才对：

```python
真官方 = "github.com/anthropics/skills" in s["url"]
```

**教训**：用间接指标（星数）去推断本质属性（是否官方），迟早出错。能直接判断就直接判断。

## 坑四：中文搜索的空格问题

给上百个 skill 做搜索时，我用了最直觉的写法：

```js
return (s.name + s.desc).toLowerCase().includes(query);
```

测试时搜"去AI味"，**0 个结果**。但明明有好几个去 AI 味改写的 skill。

原因：描述里写的是"去 **AI** 味"（中英文之间习惯加空格），而用户搜的是"去AI味"（不加）。

修复很简单，搜索前把空格都去掉：

```js
const norm = t => (t || '').toLowerCase().replace(/\s+/g, '');
```

**中文场景特有的坑**：中英文混排时空格加不加全凭习惯，做搜索必须归一化。

## 坑五：Skill 的描述，不能自己编

写中文说明时，最省事的做法是看名字猜功能。比如看到 `theme-factory`，就写"主题工厂，生成配色方案"。

但这样很容易错。我改成读每个 skill 自己的 `SKILL.md`，取里面的 `description` 字段：

```python
m = re.search(r'^description:\s*(.+?)$', content, re.M)
```

拿到官方 `theme-factory` 的真实描述是：

> Toolkit for styling artifacts with a theme. These artifacts can be slides...

——它是给**产出物**套主题的工具，不只是生成配色。我猜的那个说法虽然不算错，但会误导人。

**做整理类项目的基本要求**：描述要么来自原作者，要么明确标注是自己的理解。不要用猜测冒充事实。

## 坑六：站点改了两个月，线上一直是旧版本

这个坑代价最大。

我每天更新内容、提交、看到 GitHub 显示 commit 成功，就以为上线了。直到有一天我用无痕窗口打开自己的站点——**看到的还是两个月前的样子**。

原因是 GitHub Pages 默认走 Jekyll 处理，而我的目录结构里有它不认的文件，构建一直在失败。**而构建失败是不会给你发通知的**，仓库页面一切正常，只有专门去查 API 才看得到：

```bash
curl -H "Authorization: token $T" \
  https://api.github.com/repos/<owner>/<repo>/pages/builds | jq '.[0].status'
# "errored"   ← 已经错了两个月
```

解法就一个空文件：

```bash
touch .nojekyll && git add -f .nojekyll && git commit -m "fix pages" && git push
```

**教训**：`git push` 成功 ≠ 网站更新了。中间还隔着一次构建，而这次构建**默认静默失败**。现在我每次改完都会查一次 builds 状态，30 秒的事。

顺带说一个更难受的后果：**这两个月的访问数据全是废的**。我一度以为是内容不行，其实访客看到的根本不是我做的东西。修好之后单日访问从个位数涨到 30。

## 坑七：我宣传"每日检测"，但检测的不是最该检测的东西

这个是自己打自己脸。

我的站点首页写着"链接每日自动实测"，脚本也确实每天跑——但它只检测那 47 个**工具网址**。而站点的主体是当时那 116 个 **skill 仓库**（现在 130 个），它们从收录那天起，**一次都没复检过**。

仓库是会消失的。前面坑二里那个 404 的 skill 就是证据。我等于是在用一个真实存在的机制，为一批没被这个机制覆盖的内容背书。

补上之后第一次全量复检的结果：

```
✅ 存活 118 | ✍️ 本站原创 12 | ❌ 失效 0
⭐ 星数已过时的：63 个
🕰 超过半年没更新的：10 个
```

失效 0 个，说明这批数据当时是干净的。但**"当时是干净的"和"有机制保证它一直干净"是两回事**——差别就在于三个月后你还敢不敢让人信。

那 10 个超半年没更新的，我没有删，而是在站点上标了个 🕰。停止维护不等于没价值，但用户有权在点进去之前就知道。

同一天我还发现，我手写的 `SKILLS.md` 首行写着"114 个 Skill"，而实际已经 116 个了（今天是 130）。现在这个文件改成每天从 JSON 自动重建——**凡是会随数据变化的文字，就不该由人来写**。

## 写 Skill 时最重要的领悟：说清楚"不做什么"

前面都是技术坑，这条是设计上的。

写那 12 个原创 skill 时，我一开始只写"能做什么"。后来发现，**真正决定一个 skill 好不好用的，往往是它的边界**。

举几个实际的例子：

**记账助手**——明确写了不做什么：

> ⚠️ 这个技能只做记账整理，不做税务筹划、不做投资建议、不替代专业会计。
> 遇到这类问题时回应："这部分涉及专业判断，建议咨询会计师/税务师。我可以帮你把账目整理清楚，方便你去咨询时说明情况。"

**电商文案助手**——列了《广告法》违禁词红线：

| 类型 | 违禁词 | 替代表达 |
|------|--------|---------|
| 极限词 | 最、第一、顶级、唯一 | "我们做了 8 年" |
| 疗效词 | 治疗、杀菌、消炎 | "易清洁" |

还写了一条硬约束：**不编造参数。材质、成分、认证这些用户没提供就问，不能自己想——写错要担责。**

**家长辅导助手**——最核心的一条就是"不做什么"：

> 不直接给答案让孩子抄。直接给答案 = 帮孩子应付老师，孩子什么都没学到。

它输出的不是解题过程，是**给家长的引导话术**：

```
❌ "这题用乘法，3×4=12"
✅ "咱们先读一遍题，说说题里告诉了我们什么？"
   → "每盘 3 个苹果，一共 4 盘，那要求什么？"
   → "如果一盘一盘数，要怎么算？有没有更快的办法？"
```

还处理了一个技术文档不会写的场景：

> **家长自己情绪要炸了**：辅导作业最常见的失败不是题不会，是家长发火。
> 建议话术："我现在有点着急，咱们各自安静五分钟再说。"
> 长期关系 > 这一道题。

**教案助手**——写了防套话机制：

> ⚠️ 学情分析最容易写成套话。要写**这个年龄段学生的具体特征**，
> 例如"四年级学生已能概括段意，但对时代背景陌生，容易把'中华不振'理解为字面意思"。

以及可检测的目标写法：

> ❌ "培养学生的爱国情怀"（无法检测）
> ✅ "能结合课文和补充材料，用自己的话说出周恩来立志的原因"

## 一点感受

回头看，七个坑里有五个是同一件事：**我相信了一个没有亲自验证过的说法**——别人写的安装路径、自己写的星数判断、push 成功就等于上线、列表收录时是对的就永远是对的。

做整理类项目，最难的不是收集，是**建立机制让它不腐烂**。

AI 现在什么都敢答，所以**告诉它什么时候该停下来**，可能比告诉它怎么做更重要。

一个只写"能做什么"的 skill，用起来会发现它在你没问的地方也给意见，在它不该确定的地方也很确定。而写清楚边界之后，它反而更好用——因为你知道它在哪儿靠谱、在哪儿该自己把关。
